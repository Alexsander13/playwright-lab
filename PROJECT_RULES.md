# Правила проекта Playwright Lab

## 1. Назначение и источник истины

Playwright Lab — единый монорепозиторий русскоязычной учебной платформы и курса по автоматизации. Ученик последовательно создаёт собственный проект автотестов.

Этот файл — единый источник обязательных правил. При конфликте с планами, файлами модулей и устаревшей документацией приоритет у этого файла.

Учебный текст, который видит студент, собирается в `courseTasks`: исходные модули задают программу, а beginner-адаптер добавляет словарь, стартовое состояние, объяснение проблемы и учебные шаблоны. При редактуре проверять именно собранный урок, не считать внутренний промежуточный фрагмент самостоятельной версией материала.

## 2. Аудитория и педагогический стандарт

Курс рассчитан на **абсолютных новичков**, не предполагает знания программирования, Playwright, HTML, API, Git, CI/CD или асинхронности.

- Объяснять каждое новое понятие **до** первого применения в коде: простым языком, при необходимости с бытовой аналогией.
- Не предлагать механически копировать код: объяснять назначение решения и проблему, которую оно устраняет.
- Вводить сложность постепенно. Page Object, fixtures, mocking и другие абстракции появляются только после понятной практической потребности.
- Каждый урок ведёт к наблюдаемому, проверяемому результату в проекте ученика.
- Все пояснения, комментарии и документация — на русском; названия API, команд и технических сущностей не переводить.

### Обязательная структура урока

1. Понятный результат и реальная проблема.
2. Новые термины: 2–4 коротких определения с понятными аналогиями.
3. Краткая теория, достаточная для следующего действия.
4. Стартовое состояние и точный список изменяемых файлов.
5. Атомарные шаги: одно действие — одна причина или ожидаемый результат.
6. Видимый результат после ключевых шагов.
7. Проверяемый Definition of Done.
8. Три подсказки: направление → API/подход → целевой фрагмент кода. Первые две не раскрывают полное решение.
9. Скрытый эталонный шаблон теста в аккордеоне: полный сценарий и проверки, но без готовых локаторов.

### Правило самостоятельных локаторов

- В заданиях не давать готовый локатор. Вместо него указывать цель в кавычках: «локатор реальной кнопки входа» или «локатор поля email на текущей странице».
- Ученик находит элемент в Playwright Inspector и подставляет свой локатор в отмеченное место.
- В эталонном шаблоне также не публиковать конкретные локаторы стенда. Оставлять синтаксически понятный маркер `"ВСТАВЬТЕ … РЕАЛЬНОГО ЭЛЕМЕНТА"` и объяснять, какую проблему решает выбранный метод: роль — смысл элемента для пользователя, label — связь с подписью поля, test id — явный технический контракт.
- Единственное исключение — урок о поиске локаторов: он объясняет порядок выбора `getByRole` → `getByLabel` → `getByTestId` → `getByText`, Inspector и причины отказа от CSS/XPath.

Финальный Git-чекпоинт добавляется только в последнюю задачу модуля: `git status` → `git add -A` → `git diff --staged` → `git commit`. Сообщения коммитов соответствуют Conventional Commits.

## 3. Обязательная тестовая площадка (SUT)

Вся практика, примеры и фрагменты кода курса используют **только** `https://practice.expandtesting.com`.

- Сквозной сценарий курса: Notes App и Notes API этого домена.
- Другие страницы того же домена разрешены только как лаборатории возможностей браузера (upload/download, iframe, dialog, popup, Shadow DOM, geolocation, динамический DOM, HTTP-статусы, сетевые задержки).
- Если тема не поддерживается стендом, сначала адаптировать учебную цель под доступную страницу этого же сайта. Внешний ресурс или изолированный пример допускается только как явно отмеченное исключение с объяснением причины; он не заменяет основную практику на стенде.
- URL централизуются в `src/config/env.ts`: `BASE_URL` для UI и `NOTES_API_URL` для API. Новые URL-переменные не вводить; дочерние адреса выводить из этих двух значений.
- В тестах не прописывать домены напрямую.

## 4. Технологии и архитектура

- Платформа: Next.js App Router, TypeScript strict, Tailwind CSS.
- Backend и данные: Supabase (PostgreSQL), Server Actions и Route Handlers.
- Автотесты: Playwright Test + TypeScript; Page Object Model и пользовательские fixtures — только по мере необходимости.
- Не использовать `any`. Предпочитать понятный модульный код, KISS и DRY без преждевременных абстракций.
- Ошибки должны обрабатываться предсказуемо, с ясными сообщениями и типизированными API-ответами.

## 5. Стандарты Playwright

- Не использовать `page.waitForTimeout()`. Использовать web-first assertions и встроенное автоматическое ожидание, например `expect(locator).toBeVisible()`.
- Предпочитать пользовательские и устойчивые локаторы: `getByRole()`, `getByLabel()`, `getByTestId()` и `getByText()`; избегать хрупких CSS-цепочек и XPath. Порядок выбора объясняется до применения.
- Тесты изолированы: для данных применять уникальные идентификаторы (`runId`, `workerIndex`) и выполнять очистку после тестов.
- Явно указывать навигацию `await page.goto(...)`, когда она нужна для выполнения сценария.

## 6. Прогресс, проверка и безопасность

- Команда проверки: `npm run verify`; она синхронизирует прогресс с Supabase.
- Прогресс хранится на уровне задачи. Следующую задачу можно отметить только после всех предыдущих; статус модуля вычисляется из его задач.
- Секреты, ключи и `service_role` не попадают в клиентский код, Git, логи, diff или чат. Для внешних настроек давать пользователю точные безопасные инструкции и проверять только наличие/формат значения.
- В AI-отчёт OpenRouter разрешено передавать только текст ошибки, stack trace и минимальный DOM-фрагмент упавшего локатора после удаления паролей, персональных данных, токенов (включая `x-auth-token`) и значений окружения. Полный DOM, заголовки запросов и дампы окружения запрещены.

## 7. Текущий зафиксированный контекст

- Курс содержит 70 практических задач в модулях 0–9: 59 базовых и 11 расширенных. Модуль 10 — финальный, без формальной аттестации.
- Контент модулей 0–9 подготовлен и подключён к платформе; прохождение остаётся последовательным.
- Учебная траектория начинается с 0.1 и проходит последовательно; Git-чекпоинт Модуля 0 выполняется после 0.5. Не указывать «следующую» задачу в постоянной документации: она зависит от прогресса конкретного ученика.
- Платформа развёрнута на Vercel; Supabase, GitHub OAuth и сохранение прогресса уже реализованы.
