# Course Authoring Guidelines (Playwright Lab)

## 0. Источник истины и последовательность
- Утверждённые решения и текущий статус брать из `PROJECT_GROUND_TRUTH.md`.
- Создавать полный курс последовательно, модуль за модулем, начиная с Модуля 0; не планировать прототипы или усечённые выборки.
- Сейчас начата задача 0.1; следующая — задача 0.2 после завершения 0.1.
- Модули 0–9 включают 59 практических задач. Модуль 10 — финальное завершение курса без формальной аттестации и дополнительных задач.
- Параллельно с контентом развивать CLI-проверку `npm run verify` и синхронизацию прогресса с Supabase.

## 1. Основные принципы обучения
- **Обучение через задачи:** урок — это инженерный результат, а не лекция. Каждая задача должна приводить к видимому и проверяемому изменению в Git-репозитории ученика.
- **Не сводить урок к копированию:** не предлагать просто скопировать блок кода. Объяснять, почему выбрано архитектурное решение и какую проблему оно решает.
- **Постепенное раскрытие сложности:** вводить новые концепции поэтапно. Не вводить Page Objects, fixtures и сложный mocking до того, как ученик столкнётся с неудобством дублирования.

## 2. Структура урока или задачи
При создании и проверке задач модулей 0–9 всегда использовать эту структуру:
1. **Контекст и проблема:** какую реальную инженерную задачу решаем?
2. **Краткая теория:** только понятия, необходимые на текущем шаге.
3. **Стартовое состояние и изменения файлов:** точный список файлов для изменения.
4. **Критерии готовности (DoD):** ясные функциональные и технические критерии приёмки.
5. **Подсказки (3 уровня):** направление мысли → ссылка на API → целевой фрагмент кода. На уровнях 1–2 не давать готовое решение целиком.
6. **Финальный Git-чекпоинт модуля:** добавлять только к последней задаче модуля. Блок должен показать `git status` → `git add -A` → `git diff --staged` → `git commit`, объяснить проверку списка файлов и дать ожидаемое сообщение коммита.

## 3. Ограничения тестируемой системы (SUT)
- Использовать единственную SUT — **Expand Testing / Notes App & API** — через переменные окружения `BASE_URL` и `NOTES_API_URL`. Не добавлять сторонние тестируемые сервисы.
- Централизовать конфигурацию URL в `src/config/env.ts`; не добавлять другие переменные окружения для адресов SUT. Дополнительные endpoints выводить из `BASE_URL` или `NOTES_API_URL`.

## 4. Безопасность данных AI-репортера
- В OpenRouter разрешено отправлять только текст ошибки, stack trace и минимальный фрагмент DOM, относящийся к упавшему локатору.
- До отправки удалять пароли, персональные данные, токены авторизации (включая `x-auth-token`) и чувствительные значения окружения.
- Не отправлять полный снимок DOM, заголовки запросов или дампы окружения.

## 5. Особенность задачи 0.1
- Задача 0.1 — вводная демонстрация; коммит для неё явно не требуется. Первый Git-чекпоинт Модуля 0 находится после задачи 0.5.
- Переходить к задаче 0.2 только после завершения 0.1, сохраняя заданный порядок модуля.

## 6. Подача для начинающего (Единый стандарт уроков с 0.1 по 9.4)
- **Целевая аудитория:** ученик проходит курс последовательно и не обязан заранее знать терминологию Playwright, сетевых протоколов, API, CI/CD или асинхронного программирования.
- **Жизненные аналогии для сложных абстракций:** любые абстрактные концепции обязательно подкреплять понятными бытовыми аналогами:
  - *Promise / async / await:* чек или пейджер с номерком в кафе быстрого питания (заказ принят, но блюдо выдадут позже; `await` — подождать звонка пейджера, а не пытаться есть воздух).
  - *Promise.all:* заказ блюда в одном окне и напитка в другом одновременно; но нельзя листать одну книгу в противоположные стороны одновременно (запрет `Promise.all` для одного `page`).
  - *Interface / Type:* чертёж детали или бланк анкеты с обязательными графами.
  - *Token / Storage State:* пластиковый пропуск в спортзал или ключ-карта от отеля, полученная на стойке регистрации (показал на турникете и зашёл без повторного показа паспорта).
  - *Page Object:* пульт дистанционного управления комнатой (кнопки логина, клики и поля собраны в одном пульте, чтобы при перестановке мебели не менять все сценарии).
  - *Fixture:* служба кейтеринга или клининга, которая заранее накрывает стол перед началом теста и убирает за собой после его завершения.
  - *CI / GitHub Actions:* заводской автоматический конвейер (робот собирает деталь, проверяет на стенде и ставит отметку качества без участия человека).
  - *Trace / Artifacts:* «чёрный ящик» на борту самолёта, который включается при аварии и записывает каждое действие пилотов и приборов.
- **Порядок построения каждого урока:**
  1. *Понятный результат:* что конкретно появится в проекте после выполнения.
  2. *Зачем он нужен:* какую реальную проблему это решает на практике.
  3. *Новые слова с аналогами (блок `terms`):* 2–4 термина с простым определением и жизненной аналогией, отображаемые компактной карточкой перед теорией.
  4. *Короткая теория:* сжатое объяснение сути без перегрузки справочными деталями.
  5. *Короткие шаги:* дробление по принципу «одно действие — одна причина или ожидаемый результат». Без необъяснённых профессиональных сокращений.
  6. *Ожидаемый видимый результат:* что ученик должен увидеть в консоли, браузере или файловой системе после каждого действия.
  7. *Definition of Done (DoD):* проверяемые формулировки (строки в терминале, статус в Git, отчёт).
  8. *Три подсказки:* уровень 1 (направление мысли) → уровень 2 (API/подход без готового кода) → уровень 3 (целевой фрагмент кода). Подсказки 1 и 2 уровней никогда не раскрывают полное решение.
  9. *Свернутый блок эталонного решения:* полный код файлов прячется в аккордеон («Посмотреть эталонное решение»), чтобы стимулировать самостоятельную практику, сохраняя надежный эталон для проверки.
