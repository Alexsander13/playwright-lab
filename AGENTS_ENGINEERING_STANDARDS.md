# Инженерные стандарты и правила для AI-агентов

## 0. Ground Truth проекта
- Следовать `PROJECT_GROUND_TRUTH.md`; при конфликте исправлять устаревший документ, не переопределять утверждённые решения.
- Продукт называется **Playwright Lab** и является единым монорепозиторием платформы курса и учебного контента.
- Разрабатывать курс полноценно, модуль за модулем, начиная с Модуля 0. Прототипов и усечённых версий нет.
- Текущая задача — 0.1; следующая — 0.2 после её завершения.
- Проверка курса реализуется командой `npm run verify` с синхронизацией прогресса через Supabase.
- Адреса SUT задаются только `BASE_URL` и `NOTES_API_URL` через `src/config/env.ts`.
- Для OpenRouter разрешены только текст ошибки, stack trace и минимальный фрагмент DOM упавшего локатора после удаления секретов и персональных данных.

## 0.1 Язык и коммиты
- Все пояснения, комментарии, документация и ответы писать на русском языке; технические имена и команды не переводить.
- Сообщения коммитов оформлять по Conventional Commits.
- Отвечать кратко и сразу переходить к решению.

## 0.2 Доступы и действия пользователя
- До начала работы выявлять необходимые внешние доступы, учётные записи, настройки и значения окружения; не ждать, пока задача упрётся в них.
- Если требуется действие пользователя, заранее дать точную пошаговую инструкцию: какой сервис открыть, где выполнить действие, какие именно несекретные данные или переменные подготовить и как понять, что шаг завершён.
- Для каждого запроса явно указывать, что агент сделает после получения результата и какая проверка подтвердит успех. Не ограничиваться расплывчатыми просьбами вроде «настройте доступ».
- Никогда не просить пароли, токены, приватные ключи или секреты присылать в чат. Указать точный локальный файл и имена переменных; пользователь вводит секреты непосредственно в этот файл или защищённый интерфейс сервиса.
- После настройки проверять только наличие и безопасный формат значений, не печатать их в терминал, логи, ответы или diff. Если значение пустое или неверного формата, сообщать только имя соответствующей переменной.
- Не создавать фиктивные доступы и не считать внешнюю настройку выполненной, пока нет подтверждения проверкой.

## 1. Стек и архитектура
- **Платформа:** Next.js (App Router), TypeScript в строгом режиме, Tailwind CSS. Не использовать тип `any`.
- **База данных и backend:** Supabase (PostgreSQL), Server Actions и Route Handlers.
- **Тестирование:** Playwright Test (TypeScript), Page Object Model (POM), пользовательские fixtures.

## 2. Качество кода
- **DRY и KISS:** писать модульный, понятный код. Не вводить абстракции преждевременно; например, создавать Page Objects, когда дублирование действительно затрудняет поддержку.
- **Обработка ошибок:** обрабатывать ошибки предсказуемо, показывать пользователю ясные сообщения и использовать типизированные ответы API.
- **Безопасность:** не раскрывать на клиенте секреты, приватные ключи и ключ Supabase `service_role`. Корректно использовать переменные окружения.

## 3. Стандарты Playwright-тестов
- **Без нестабильных ожиданий:** запрещено использовать `page.waitForTimeout()`. Предпочитать web-first assertions, например `expect(locator).toBeVisible()`, и встроенное автоматическое ожидание.
- **Устойчивые локаторы:** предпочитать `getByTestId()`, `getByRole()` и семантические атрибуты хрупким цепочкам CSS/XPath.
- **Изоляция данных:** тесты должны быть независимыми. Использовать уникальные идентификаторы (`runId`, `workerIndex`) и очищать данные после выполнения.
